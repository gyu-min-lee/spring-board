# Spring Boot Board API

Spring Boot 기반의 REST API 게시판을 구현한 학습 프로젝트입니다.

게시판의 기본적인 CRUD 구현부터 JPA를 이용한 데이터 처리, JWT 기반 인증/인가, 예외 처리와 Service 레이어 테스트까지 직접 구현하며 백엔드 개발의 전반적인 흐름을 익히는 것을 목표로 진행했습니다.

단순히 기능을 구현하는 것뿐 아니라 개발 과정에서 발생한 문제와 시행착오를 직접 해결하고 정리하는 데 중점을 두었습니다.

---

## 기술 스택

- **Language:** Java 21
- **Framework:** Spring Boot 4.1.0
- **ORM:** Spring Data JPA (Hibernate)
- **Database:** H2 (개발 및 테스트용 인메모리 DB)
- **Security:** Spring Security, JWT (jjwt), BCrypt
- **Test:** JUnit5, AssertJ
- **Build Tool:** Gradle

---

## 구현 완료 기능

- **회원 관리**
  - 회원가입 (비밀번호 BCrypt 단방향 암호화 적용)
  - 로그인 (JWT 토큰 발급 및 필터를 통한 검증)
- **게시글 관리**
  - 게시글 CRUD (작성자 본인 검증 보안 로직 포함)
- **댓글 관리**
  - 댓글 CRUD (작성자 본인 검증 보안 로직 포함)
  - 특정 게시글의 댓글 목록 조회
- **예외 처리**
  - `GlobalExceptionHandler`를 통한 전역 예외 처리
- **테스트**
  - Service 레이어 단위 테스트 작성 (회원/게시글/댓글 기능, 성공 및 실패 케이스 포함, 총 24개)

## 트러블슈팅 & 시행착오

### 1. SQL 예약어 충돌로 인한 테이블 생성 실패
- **문제 상황:** 엔티티명을 `User`로 지정하여 서버를 실행했으나, H2(및 다수의 RDBMS)에서 `USER`가 SQL 예약어로 지정되어 있어 테이블 생성 시 Syntax Error가 발생함. 이로 인해 일부 테이블만 생성되거나 외래키 제약조건 설정이 실패함.
- **원인 분석:** 데이터베이스 시스템이 인식하는 예약어와 엔티티 테이블명이 충돌함.
- **해결 방안:** 엔티티명을 `Member`로 리네이밍하여 SQL 예약어 충돌 문제를 근본적으로 회피함.

### 2. 게시글 및 댓글 소유권 검증 누락 (보안 취약점)
- **문제 상황:** 인증 토큰을 통해 '로그인 여부'만 확인한 채 수정/삭제 API를 구현하여, 로그인한 사용자라면 타인의 게시글이나 댓글도 임의로 수정 및 삭제할 수 있는 상태였음.
- **원인 분석:** 서비스 레이어의 수정·삭제 로직에 '대상 리소스의 실제 소유주와 현재 요청한 유저가 일치하는지' 비교하는 검증 로직이 누락됨.
- **해결 방안:** Controller 계층에서 `Authentication` 객체를 통해 로그인한 사용자의 식별자인(`username`)를 추출하여 Service로 전달함. Service 내부에서 리소스 작성자의 `username`과 대조한 뒤, 불일치할 경우 커스텀 예외를 발생시키도록 보안 로직을 보완함. (댓글 기능에도 동일 패턴 적용)

### 3. 테스트 코드 간 DB 상태 오염 문제
- **문제 상황:** 동일한 테스트 클래스 내에서 여러 개의 `@Test` 메서드를 함께 실행할 때, 선행 테스트에서 생성한 데이터가 DB에 남아 후속 테스트에서 `이미 존재하는 아이디입니다` 같은 중복 예외가 발생함.
- **원인 분석:** 각 테스트가 독립적인 트랜잭션으로 실행되고 롤백되지 않아, 한 테스트에서 생성한 데이터가 이후 테스트에 남아 테스트 간 상태가 격리되지 않음.
- **해결 방안:** 테스트 클래스에 `@Transactional` 어노테이션을 추가하여, 각 테스트가 종료될 때마다 자동으로 롤백을 수행하도록 설정함. 이를 통해 각 테스트가 독립적인 DB 상태에서 실행되도록 보완함.

### 4. 테스트 코드의 검증 범위 부족
- **문제 상황:** 댓글 삭제 성공 테스트 작성 시, 게시글에 댓글이 1개만 있는 상태로 검증하여 "삭제 후 목록이 비어있음"만 확인함. 이 경우 특정 댓글이 정확히 삭제되었는지까지 검증하지 못하는 구조였음.
- **원인 분석:** 검증 대상 데이터가 1건뿐이라, "특정 댓글만 삭제되었는가"가 아니라 "전체 댓글이 삭제되었는가"를 확인하는 셈이 되어 삭제 로직의 정확성을 충분히 보장하지 못함.
- **해결 방안:** 댓글을 2개 이상 준비한 뒤 특정 댓글만 삭제하고, 남은 댓글의 개수와 식별자(id)까지 함께 검증하도록 테스트를 보완함.
